# Data Model: Twinery MCP Server v1.0 MVP

**Feature**: 001-mcp-server-mvp
**Date**: 2026-04-23
**Source of truth for runtime types**: `src/twine/adapter.ts` (shapes derived from
IFTF Twine 2 JSON output spec, via `extwee`).

All entities below map 1:1 to the Twine 2 JSON Output spec unless flagged as
"server-internal." Server-internal entities do not appear in exported artefacts.

---

## Story (server-internal state + spec-level entity)

The single active story held in memory (per Constitution: single-story model).

| Field | Type | Required | Source | Validation |
|-------|------|----------|--------|------------|
| `name` | string | yes | author at `create_story` | non-empty, ≤ 200 chars |
| `ifid` | string | yes | `create_story` or auto-generated by `extwee` | 8–63 chars of `[0-9A-Z-]` per Twine 2 HTML spec |
| `format` | enum | yes | author | one of `Harlowe`, `SugarCube`, `Chapbook`, `Snowman` |
| `format_version` | string | yes | defaults per format | semver (e.g. `3.3.8`) |
| `start_passage` | string | yes | defaults to first passage created; updated by `set_start_passage` or by `rename_passage` when renaming the current start | MUST name an existing passage |
| `tag_colors` | `Record<string,string>` | no | tools | Twine-recognised color strings |
| `zoom` | number | no | default `1` | `0 < zoom ≤ 5` |
| `style` | string | no | managed by `images/render.ts` when first image placeholder is added | CSS text |
| `script` | string | no | deferred; placeholder for future features | JS text |
| `passages` | `Passage[]` | yes | built by passage tools | unique names (case-sensitive) |
| `story_slug` | string | server-internal | derived from `name` at create / rename | kebab-case, URL-safe; used in image-asset paths |

**Invariants**:
- `start_passage` resolves to an existing passage at all times. Enforced post-
  mutation by the server.
- Passage names are unique within a story. Enforced at `create_passage` and
  `rename_passage` time with a clarification-based refusal (per FR-006) if the
  new name collides.
- `ifid` is immutable after creation.

**State transitions**: none (Story is a container; passages hold the state
transitions implicitly via link graph).

## Passage (spec-level entity)

A node in the story graph.

| Field | Type | Required | Source | Validation |
|-------|------|----------|--------|------------|
| `name` | string | yes | author | non-empty, unique within story, `[`, `]`, `{`, `}`, `\` backslash-escaped in Twee serialisation |
| `tags` | `string[]` | no | author | each tag is non-empty, no whitespace |
| `position` | `{x:number,y:number}` | no | auto-assigned by `create_passage` to avoid overlap if omitted; authors may override | both values ≥ 0 |
| `size` | `{w:number,h:number}` | no | defaults to `{100,100}` per Twine editor convention | both values > 0 |
| `text` | string | no | author via `create_passage` / `update_passage` | UTF-8; contains outgoing links as format-specific syntax |
| `image_placeholders` | `ImagePlaceholder[]` | server-internal | `add_image_placeholder` | see below |

**Invariants**:
- Outgoing links embedded in `text` MUST use the link syntax of the story's
  declared format. The server enforces this in `link_passages`, never by
  rewriting raw text the LLM has supplied elsewhere.
- Renaming a passage rewrites every incoming `[[...]]` in every other passage's
  `text` and, if needed, the story's `start_passage`. Atomic from the caller's
  point of view.

**State transitions**: text / tags / position / size can be mutated freely via
`update_passage`. `rename_passage` and `delete_passage` are separate tools
because they have graph-integrity side effects.

---

## Link (implicit, managed by server)

A directed edge from one passage to another. Twine stores links inline in the
source passage's text; this project manages them as a first-class graph for
integrity operations even though they are not a separate entity at rest.

| Field | Type | Source | Notes |
|-------|------|--------|-------|
| `from_passage` | string | server parse | name of the passage whose text contains the link |
| `to_passage` | string | server parse | parsed out of `[[...]]` syntax |
| `display_text` | string \| null | server parse | the `text` in `[[text->target]]` or `[[text\|target]]`; null for `[[target]]` |

**Not persisted** as a separate artefact; regenerated on demand by parsing
passage text through extwee.

**Validation**:
- `validate_story` reports links whose `to_passage` does not exist (broken).
- `link_passages` uses the story's declared format to choose arrow (`->`) vs
  pipe (`|`) syntax.

## ImagePlaceholder (server-internal; part of Passage state)

A marker for an image the author has not yet provided. The placeholder emits
HTML into the passage text so the played story has a deterministic attempt-load
target.

| Field | Type | Required | Source | Validation |
|-------|------|----------|--------|------------|
| `label` | string | yes | author | kebab-case, `^[a-z0-9][a-z0-9-]{0,62}$`; unique within the parent story (per R3 + FR-007) |
| `expected_filename` | string | yes | derived | `<label>.<ext>` where `<ext>` is the first of `png`, `jpg`, `jpeg`, `gif`, `webp` to exist on disk at play time (the played HTML `<img>` uses the `label.png` form and the fallback stylesheet hides it if missing) |
| `expected_folder` | string | yes | derived | `<saved-story-dir>/assets/<story_slug>/` |
| `passage_name` | string | yes | add call | MUST exist at creation time |
| `insertion_index` | number \| null | no | author or end-of-text | character offset in `passage.text`; `null` means append |

**Invariants**:
- `label` is unique across all placeholders in the active story. Collision
  triggers FR-006 clarification; no silent rename (per resolved Q2 answer).
- On `rename_story` (not part of v1.0) or export-path change, placeholder
  folder paths MUST be re-reported to the author. v1.0 freezes placeholder
  paths once the story is saved for the first time.

**State transitions**:
- Added via `add_image_placeholder`. Removed by removing its emitted HTML via
  `update_passage` (server detects and cleans up the placeholder record; not a
  dedicated tool in v1.0).

## Guide (server-internal; also exposed as MCP resource)

The LLM-facing document listing every tool and its contract.

| Field | Type | Source |
|-------|------|--------|
| `content_markdown` | string | generated by `src/guide/build.ts` from `src/guide/registry.ts` + zod schemas |
| `static_path` | filesystem path | `docs/GUIDE.md` (committed to the repo) |
| `resource_uri` | URI | `twinery://guide` |
| `mime_type` | string | `text/markdown` |

**Invariants**:
- Static file content is byte-identical to what the resource handler returns.
  Enforced by `tests/contract/guide-drift.test.ts` (R6).
- Every tool registered in `src/guide/registry.ts` appears in the guide; every
  tool mentioned in the guide exists in the registry.

## ClarificationRequest (server-internal + part of tool-response contracts)

The structured form of "the server needs info before it can proceed."

| Field | Type | Required | Notes |
|-------|------|----------|-------|
| `clarification_id` | UUIDv4 | yes | stable across retries; used by `respond_to_clarification` |
| `question` | string | yes | short, user-facing |
| `valid_answers` | `string[]` \| null | no | enum of acceptable answers where the space is finite (e.g., the four story formats) |
| `free_text_allowed` | boolean | yes | when `valid_answers` is null or non-exhaustive |
| `originating_tool` | string | yes | the tool that emitted this request |
| `originating_args` | object | yes | the partial args the LLM had already supplied; replayed when the clarification is resolved |
| `transport` | `"elicitation"` \| `"fallback"` | server-internal | chosen at session init (per R1) |

**Lifecycle**:
1. Tool call lacks required info → server constructs `ClarificationRequest`.
2. If session transport is `elicitation`, the SDK's elicitation primitive is
   invoked; the author's answer resolves inline and the tool call continues.
3. If session transport is `fallback`, the tool call returns a structured
   response with `kind: "clarification_needed"` and the full
   `ClarificationRequest` embedded. The client calls the dedicated
   `respond_to_clarification` tool with `clarification_id` + the author's
   `answer`; the server replays the original tool with the answer merged.

**Invariants**:
- Server MUST NOT persist any clarification longer than the session; they live
  only in memory.
- Two concurrent clarifications on the same originating tool+args are permitted
  but each receives a unique `clarification_id`.

## Relationships

```text
Story 1───* Passage
Story 1───1 Guide (singleton per server)
Passage *───* Link  (derived from text; not persisted)
Passage 1───* ImagePlaceholder
```

No many-to-many relationships persist on disk; the entities that round-trip
through `extwee` (Story, Passage, Link) are exactly the spec-level entities.
